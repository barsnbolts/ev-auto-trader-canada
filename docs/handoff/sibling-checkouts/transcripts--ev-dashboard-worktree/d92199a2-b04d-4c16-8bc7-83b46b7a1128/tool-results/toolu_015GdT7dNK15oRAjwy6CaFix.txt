## 0.6. Native app strategy — Apple Silicon + "truly native" roadmap

**Ian's goal:** offload as much processing as possible to M1 hardware; move toward a proper Mac app, not just a website in a shell.

**Honest assessment of what Tauri 2 gives you today:**

Tauri 2 compiles the Rust backend natively to `aarch64-apple-darwin` — that's real ARM64 code running on your M1's performance cores. The React/TypeScript frontend runs in WebKit (Safari's engine), which is already GPU-accelerated by Metal. So the app is *less* of a "website in a shell" than it looks — WebKit + Metal is what Safari uses.

**What can be offloaded to Apple Silicon hardware RIGHT NOW (within Tauri):**

| Workload | Current | Native option | Gain |
|---|---|---|---|
| **Thermal physics model** | TypeScript in V8 (JS engine) | Rust plugin + Apple Accelerate vDSP | 2–3× faster; more importantly, moves physics to ARM64 native |
| **Map + range rings** | Leaflet/MapKit JS | MapKit JS already uses Metal via WebKit; MapKit native (SwiftUI) is 30–40% better FPS | JS is fine for 20–50 vehicles |
| **Interpolation loops** | JS for-loops | Rust SIMD (ARM NEON via std::simd) or Apple vDSP | Clean win for batch processing |
| **Battery degradation** | JS lookup | Rust pre-computed polynomial | Negligible at 20 vehicles |

**What Tauri 2 on macOS CANNOT do (important constraints):**
- No Swift plugins — Tauri macOS is Rust-only. Swift plugins exist on iOS Tauri (inside a Swift app context) but not on macOS desktop.
- No direct Metal compute shaders from Tauri plugins.
- No CoreML access from Tauri/Rust (would need Swift/Objective-C FFI).

**Plan: two-phase approach**

**Phase 1 — Tauri enhanced with Rust native (Cluster D, do now):**
- Move the thermal physics model (`thermal.ts`) to a Tauri Rust plugin.
- Rust compiles ARM64 native, can use Apple Accelerate `vDSP_vintb` for the interpolation loops.
- Frontend calls `invoke("compute_thermal", {...})` instead of the TS function.
- Result: physics runs on M1 performance cores, not in V8. Battery life slightly better, instant compute even at 200+ vehicles.
- Tests: Rust unit tests for the physics model replace the Vitest golden tests.

**Phase 2 — Full SwiftUI rewrite (Cluster G, after Cluster F, Ian-decision):**
- Build a true SwiftUI Mac app: NavigationSplitView for the brand list, Swift Charts for charging curves, MapKit native for range rings, native Dark Mode / accent colors.
- Estimated effort: 6–8 weeks of coding (the TypeScript spec + physics Rust plugin become the design doc).
- Trigger: after all features in D/E/F are working and Ian has used the app for a month. "Does it feel like a Mac app?" — if the answer is yes, stay. If no, rewrite.
- Ian's learning path: TypeScript → Rust (Cluster D) → Swift (optional Cluster G). Each step teaches real systems skills.

**Decision for Cluster D kickoff:**
- Add **D0** (new): Create Tauri Rust plugin for `compute_thermal`. This is the "offload processing" item Ian wants, and it's achievable in one session.

## 1.9. Specs — the design artifact that guides each feature

**What a spec is, in plain English:** a short markdown document (usually 1–2 pages) that describes *what* a feature does before we build *how*. It's the "requirements + acceptance criteria" doc — the thing we aim at. A spec answers "what problem does this solve, what does it look like, how do we know it's done?" *without* prescribing the implementation.

**Why they help us specifically:**
- **Ian reads the spec first** — before I write code, he sees the feature in plain English and can redirect if the scope is wrong. Faster than reviewing code.
- **Claude aims at the spec** — implementation doesn't drift. Tests match the spec's acceptance criteria.
- **Cache-friendly** — specs are stable once approved; prompt caching loves stable files.
- **Cross-session durable** — a future Claude session reads the spec, not my prior chat context.
- **Teach mechanism** — reading specs is how Ian learns "what this feature actually does" without needing to parse TypeScript.

**Location:** `specs/` at project root. One file per significant feature or cluster. Naming: `specs/<cluster>-<shortname>.md` or `specs/<item-id>-<shortname>.md`.

**Template:**

```markdown
# <ID> — <Title>

## Goal
One paragraph: what problem this solves, for whom, and why now.

## User-visible behavior
Plain-English. What Ian (or mom) notices change in the app.

## Acceptance criteria
1. Testable statement.
2. Testable statement.
3. …

## Inputs / state touched
Files, store keys, data fields.

## Outputs
What the user sees / what data changes.

## Dependencies
What must already exist.

## Test plan
Which of the 8 test layers applies; specific fixtures.

## Open questions
Resolved before implementation or flagged as Ian-decisions.

## Done when
Concrete green-check list that gates completion.
```

**Workflow integration:**
1. **Cluster kickoff.** I write (or update) the cluster-level spec: `specs/cluster-A-foundation.md`. Ian reads it. ~5 minute review.
2. **Per-significant-item spec.** For items with user-visible changes (C1 cost-per-100km, C2 breakdown drawer, D3 map panel, E2 trip planner, F1 mom mode), a dedicated spec lives in `specs/`.
3. **Bug-fix items** (B-01, rollupConfidence) get a micro-spec inline in the git commit message — no separate file.
4. **Spec precedes code.** If I catch myself coding without the spec existing, I stop and write it first.
5. **Specs are versioned.** On material change, the spec gets a `## Changelog` footer — so we can look back at what the feature used to be.

### 💎 UI elegance — woven through, swept at the end

Locked-in principles enforced on every UI touch:
- **Spacing:** 4/8/16/24/32/48 px grid. No ad-hoc margins.
- **Typography:** system stack for prose (−apple-system, SF Pro, Inter fallback); SF Mono / JetBrains Mono for numerics. Scale 32/24/18/15/13/11.
- **Color:** one accent, ink-900→ink-50 ramp, semantic confidence (emerald / amber / rose). Never invent hex inline.
- **Motion:** 150–250ms ease-out; subtle spring on tray; smooth slider counter; animated range-ring radius.
- **Focus states:** visible ring on every interactive element (HIG + WCAG).
- **Empty states:** every "no data" moment designed.
- **Loading states:** skeleton placeholders, not spinners.
- **Contrast ratios:** ≥4.5:1 normal text, ≥3:1 large text, ≥3:1 focus indicators.

Enforced per cluster; dedicated sweep in F6.
