## H11 — Stress-test + empirical learning loop (calibration of the recommender)

**Goal.** Replace the hand-tuned constants in `cost_model.py` (TASK_TOKENS) and `task_complexity.py` (TASKS minimums) with empirically-learned numbers. The system should observe what each (model, effort) pair actually achieves on this codebase, and recalibrate so future recommendations are based on reality, not guesses. Asymmetric aggression: **conservative when lowering** (need ≥3 successful observations at a cheaper level before bumping the min down), **eager when raising** (any failure at current level immediately raises the min for that tag). This satisfies Ian's "run as long as possible on the cheapest model" goal without locking in a bad downshift after one lucky run.

### Two halves

**Half A — Passive learning (always-on, every milestone).**

Each milestone records one observation row capturing how the task actually went. The calibrator runs after every Nth milestone and proposes/applies updates to the constants.

**Half B — On-demand stress test (active probing).**

When Ian wants to verify a level's limits before trusting it, `scripts/stress_test.py` prints a small battery of canonical tasks for the current detected level. I run them at that level, score against objective rubrics, log into the same observation stream. Useful for first-time level-changes or after a long stretch on one level.

### Observation schema

Each row in `logs/task_observations.jsonl` (NDJSON):

```json
{
  "ts": 1777060000000,
  "milestone_id": "H11",
  "model": "claude-opus-4-7[1m]",
  "effort": "xhigh",
  "task_tag": "architectural-refactor",
  "passed_first_try": true,
  "indirect": {
    "git_lines_changed": 540,
    "wall_clock_min": 22,
    "completed_turns_delta": 18,
    "milestone_exit_code": 0
  },
  "self_estimate": {
    "cost_tokens": 35000,
    "confidence": "medium"
  },
  "source": "milestone"  // or "stress_test"
}
```

`self_estimate` comes from a new `--cost-tokens` and `--confidence` flag on `milestone.py` that I fill out per turn (subjective best-guess, rounded to 5k). Indirect fields are computed from git + session JSON automatically.

Combined cost units used by the calibrator: `max(self_estimate.cost_tokens, indirect_estimate)` where the indirect estimate is a heuristic combining git-lines × 50 + turns × 1500. Conservative (favours the larger number).

### Calibration logic

`scripts/calibrate.py` runs after every 5 milestones (and on `--force`). Reads `logs/task_observations.jsonl`, groups by `task_tag` and current `(model, effort)`. For each group:

**TASK_TOKENS update (cost estimates):**
- New estimate = median of last 10 observations' combined cost units, rounded to nearest 1k.
- Apply only if it differs from current by ≥20 % AND there are ≥5 observations.
- Atomic file rewrite of `cost_model.py` TASK_TOKENS dict; full backup written to `cost_model.py.bak.<ts>`.

**TASKS minimums update (capability bar):**
- DOWN: need ≥3 *consecutive* successful observations at a strictly cheaper (model, effort) for the same tag. A single failure at the cheaper level resets the counter.
- UP: a single failure at the *current* level for a given tag immediately raises that tag's min to the next tier UP.
- All updates written via atomic file rewrite of `task_complexity.py` TASKS dict; backup written to `task_complexity.py.bak.<ts>`.

Every change appended to `logs/calibration_changes.md` (gitignored) with timestamp + before/after diff + N-observation count + brief reason.

### Stress test (active probing)

`scripts/stress_test.py [--tag <tag> | --suite quick]` prints a numbered checklist of canonical tasks for the *currently detected* model+effort:

1. Each task has an objective rubric (e.g., "code compiles", "test passes", "answer matches gold value", "summary ≤ 100 words and includes specific term").
2. I work through them, logging each into `logs/stress_runs.jsonl` with the observation schema above.
3. At the end, automatically invokes `scripts/calibrate.py --include-stress` to fold those observations into the regular calibration.

**Initial canonical battery (quick-suite, ~5 tasks):**

- `t1-rename` — rename a single symbol across 3 files (objective: tsc green after rename).
- `t2-test-mirror` — add a vitest case mirroring an existing test for a new edge case (objective: test runs + asserts).

Each task has an estimated `task_tag` so the observation can be slotted into the right TASK_TOKENS bucket.

### Conservative-aggression rules (concrete numbers)

| Rule | Trigger | Action |
|---|---|---|
| Lower min for tag X | ≥3 consecutive `passed_first_try=true` observations of tag X at a level strictly cheaper than current min | Set min to the cheaper level. Reset counter. |
| Raise min for tag X | Any single `passed_first_try=false` observation at the current min level | Bump min UP one tier. Reset down-counter. |
| Update TASK_TOKENS for tag X | ≥5 observations AND median changes by ≥20 % from current value | Replace constant. |

The "consecutive" requirement means a single bad run at the lower level *immediately* resets the down-counter — so we won't oscillate around a flaky boundary. The "any failure raises" rule errs on the side of safety: if I stumble at the supposed min level, the system pushes the bar up rather than rationalising.

### Self-estimate convention

When invoking `milestone.py` I include `--cost-tokens` based on a rough subjective gauge:

- **2k**: trivial commit, ≤3 tool calls, no thinking.
- **5k**: small UI tweak, focused.
- **10k**: a few file edits, some search.
- **20k**: multi-file feature, several iterations.
- **40k**: spec-writing or significant refactor with branching exploration.
- **80k+**: deep planning session with research agents.

Confidence values: `low` (wild guess), `medium` (reasonable estimate), `high` (I tracked carefully).

The calibrator weights `high`-confidence self-estimates 3× over `low`-confidence when computing medians.
