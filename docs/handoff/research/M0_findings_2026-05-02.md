# M0 — GraphQL response-body probe + SSR daysOnMarket audit (2026-05-02)

**TL;DR.** GraphQL bodies cannot be captured cleanly without a CDP-level
hook (the JS-injection hook wipes on every full nav, and AutoTrader's
sort/filter UI uses cached SSR data — no fresh GraphQL fires). But the
question the probe was supposed to answer is now settled by direct
inspection of `__NEXT_DATA__`:

> **Decision: GraphQL probe unusable as a daysOnMarket source. Default to
> M3 snapshot-diff. M2 Apify confirms whether the paid actor returns
> daysOnMarket directly.**

## What was probed

Live session against:
- `https://www.autotrader.ca/cars/?make=Hyundai&model=Ioniq+5&prv=Ontario`
- One detail page: `https://www.autotrader.ca/offers/hyundai-kona-gasoline-white-e1a47973-bd1d-4012-becb-424f577cc919`
- `https://www.autotrader.ca/cars/?make=Kia&model=EV6&prv=Ontario&rcp=15`

Tools: Chrome MCP (`mcp__Claude_in_Chrome__*`). HEAD `cd2936e6`, branch
`claude/verify-environment-setup-oTu3S`.

## What was confirmed

### 1. The two GraphQL endpoints fire on page load

`mcp__Claude_in_Chrome__read_network_requests` confirmed three POSTs per
page load:

- `https://listing-search.api.autoscout24.com/graphql` (200)  ×2
- `https://www.autotrader.ca/listing-search-api/graphql` (200)  ×1

**MCP limitation.** `read_network_requests` returns URL/method/status
only — no response body, no request body. To get bodies a JS hook must
be installed BEFORE the requests fire, OR a CDP-level
`Network.getResponseBody` call is needed (not exposed by Chrome MCP).

### 2. JS hook approach hit two structural blockers

- **Full-nav wipes hook.** Pagination via the page's "Next" button is
  full nav (`https://www.autotrader.ca/cars/<page-2-url>`), not in-page
  SPA — the new `window` is fresh, hook gone.
- **In-page sort/filter doesn't fire fresh GraphQL.** Changing the sort
  dropdown to "Posted Date: New to Old" produced 0 captured calls.
  AutoTrader's Next.js client filters/sorts the SSR-cached `__NEXT_DATA__`
  array client-side; only navigation triggers a fresh server fetch.

### 3. Same-origin GraphQL introspection hit Imperva

Sending `{ query: "{ __schema { ... } }" }` from the page's own JS
context to either GraphQL endpoint (with `credentials: 'include'`)
hangs the renderer and times out at 45s. Almost certainly an Imperva
bot challenge on POSTs without the right hash header.

### 4. SSR `__NEXT_DATA__` per-listing payload — definitive field audit

Search-results SSR (`/cars/?make=...&model=...`) embeds per-listing data
under `props.pageProps.listings[]`. Recursively collected every key
across the first listing (depth 5):

**Time-related keys on a search-results listing:**
- `tracking.firstRegistration` — vehicle's first registration date
  (NOT listing date)
- `vehicle.mileageInKm` — odometer (not time)
- That's it.

**No `postedAt`, `firstSeen`, `daysOnMarket`, `daysOnLot`, `listingDays`,
`createdAt`, or any equivalent.**

### 5. SSR `__NEXT_DATA__` per-listing DETAIL page — schema HAS the field, value is null

Visiting `https://www.autotrader.ca/offers/<slug>-<uuid>` reveals
`props.pageProps.listingDetails.availability` carries:

```json
{
  "rawFromDate": null,
  "fromDate": null,
  "inDays": null
}
```

`inDays` is the field that *would be* daysOnMarket. The schema is wired,
the data is null on every `/offers/` URL we sampled. This matches the
already-documented `BLOCKERS_MEDIUM.md #2`: "/offers/ listing pages
don't expose daysOnLot or MSRP".

### 6. URL-family observation — every listing is on `/offers/`

Sampling 20 Kia listings from a search-results page: 100% of `listings[].url`
values point to the `/offers/` namespace (one slug per listing, all UUID-tagged).
There is no `/cars/<id>/` or `/a/<id>/` URL family in current AutoTrader
Canada output. So the "maybe non-`/offers/` URLs have inDays populated"
hypothesis is moot — there are no non-`/offers/` URLs.

### 7. Side observation: search-results query-param filter is broken

`?make=Kia&model=EV6` returned 5,798 results spanning EV4, Sorento,
Sportage, Carnival, Forte, etc. The `model=` filter is silently
ignored when supplied via querystring. **Implication for M2:** Apify
input MUST use path-form URLs (`/cars/kia/ev6/on/?rcp=100`), which is
already what `docs/apify_inputs/ontario_full.json` does. Don't rewrite
to query-param form.

## Decision matrix update

| Path                          | Status                                     |
|-------------------------------|--------------------------------------------|
| GraphQL response bodies       | **UNUSABLE** without a CDP-level pre-load hook (Chrome MCP doesn't expose). |
| SSR `__NEXT_DATA__` daysOnMarket | **MISSING** — `availability.inDays` schema exists, always null on `/offers/`. |
| Snapshot-diff (M3)             | **GO** — daysOnMarket = today − first_seen, walked across `data/snapshots/*.json` filtering by stable `u-at-<8hex>` IDs. Free, robust, self-healing. |
| Apify (M2)                     | **GO for confirmation** — actor docs say `daysOnMarket` is in the dataset. Tiny sample run (~$0.10) confirms whether the field is populated for ON/HK listings. If yes, complements snapshot-diff with a same-day signal until snapshots accumulate. |

```js
const nd = JSON.parse(document.getElementById('__NEXT_DATA__').textContent);

console.log(Object.keys(first));   // No daysOnMarket-equivalent.

// Run on any /offers/<slug>-<uuid> detail page
const nd2 = JSON.parse(document.getElementById('__NEXT_DATA__').textContent);
console.log(nd2.props.pageProps.listingDetails.availability);
// → { rawFromDate: null, fromDate: null, inDays: null }
```
